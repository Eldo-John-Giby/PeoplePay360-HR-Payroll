# PeoplePay360 — HR & Payroll Platform

FastAPI + PostgreSQL 16 + SQLAlchemy 2.0 + Alembic + Pydantic v2.

This is the **database foundation + core infrastructure slice** (Eldo's):
all `app/models/`, `app/core/`, the first Alembic migration, seed data,
`app/main.py`, and the Auth/RBAC module. The other three engineers build on
top of this without touching the shared files (see
`00_ARCHITECTURE_AND_WORKFLOW.md`).

---

## Quick start

```bash
docker compose up --build          # Postgres 16 + app; runs migrate + seed + uvicorn
# Interactive docs:
open http://localhost:8000/docs
```

`docker compose up` is the whole demo: it applies `alembic upgrade head` on a
fresh database, seeds realistic demo data (idempotent), and boots the API.

Local (non-container) workflow, against the same `db` service:

```bash
docker compose up -d db
alembic upgrade head
python -m app.seed.seed_data
uvicorn app.main:app --reload
```

> **No-Docker launcher removed**: the former `dev.py` (embedded-Postgres
> bootstrap via `pgserver`) was deleted because its embedded build ships no
> contrib modules — the initial migration enables `pg_trgm`, so the launcher's
> schema diverged from the real one. Docker (or a system Postgres) is the
> supported path above.

## Design decisions (documented tradeoffs)

### Intentional denormalization (schema doc §5)
1. **`payslip_lines.code/name/category`** snapshot the salary rule at compute
   time — payslips are legal/historical records; editing a rule next month
   must not retroactively rewrite a paid payslip.
2. **`attendances.worked_hours` + `.status`** are computed at check-out and
   stored — a later change to the employee's working schedule must not
   silently rewrite historical attendance.

### Deliberately NOT stored (the counter-examples)
- **Leave balance** → SQL view `v_time_off_balances` (allocated − taken, only
  approved rows; allocations filtered by `valid_to`). A stored running total
  would drift out of sync. Query it via `app.models.views.TimeOffBalanceView`
  or raw SQL.
- **Weekly schedule hours** → SQL view `v_working_schedule_hours` (plus a
  Python convenience property on `WorkingSchedule` for already-loaded rows).

### One-running-contract rule
Enforced at the DB level with a **partial unique index**
`uq_contracts_one_running_per_employee ON contracts (employee_id)
WHERE status = 'running'` — a second running contract is structurally
impossible (service layer translates the violation into a friendly 409).
**Future hardening:** a full non-overlapping-date-range `EXCLUDE` constraint
using `btree_gist` would also reject overlapping *different-status* contracts;
deliberately skipped for the 24h hackathon.

### `payslips.contract_id` is NULLABLE
An employee selected into a payrun with no running contract still gets a
payslip carrying a `missing_contract` warning and zero/blocked salary
(schema doc edge cases) — so the FK must be able to be NULL.

### Roles vs permissions
`require_roles(...)` (OR across a user's roles) is the primary gate —
matching the 5-role model from the problem statement. A finer-grained
`require_permission(...)` dependency also exists and the seed wires a
`role_permissions` matrix for 11 permission codes (e.g. `payrun.write`,
`salary_rule.write`, `user.manage`), so both styles are available and
demonstrable. The user-management endpoints use `ADMIN` role checks.

### Emails
`users.email` / `employees.work_email` are `VARCHAR` with **app-level
lowercasing** on write + a DB unique constraint, instead of the `citext`
extension — one less extension to manage; identical behavior for logins.

### Optimistic locking
`version_id` columns + `__mapper_args__ = {"version_id_col": version_id}` on
the high-contention tables named in the architecture doc §5.1: Contract,
Payrun, Payslip, TimeOffAllocation.

### Password hashing
bcrypt directly (12 rounds). Passlib 1.7.4 is unmaintained and breaks with
`bcrypt>=4.1`, so `security.py` uses `bcrypt.hashpw/checkpw` instead.

## Indexing checklist (all applied)

- Every FK column → B-tree index (explicitly in the migration)
- `contracts`: partial unique `(employee_id) WHERE status='running'`
- `attendances`: composite `(employee_id, check_in)` + `(status)`
- `time_off_allocations` / `time_off_requests`: composite
  `(employee_id, time_off_type_id, status)` / `(employee_id, status)` +
  `(time_off_type_id)`
- `payslips`: unique `(payrun_id, employee_id)` + composite
  `(employee_id, period_start, period_end)` for overlap checks
- `payruns`: `(status)` + `(period_start, period_end)`
- `salary_structure_rules`: composite `(salary_structure_id, sequence)`
- `employees.full_name`: GIN trigram index (`pg_trgm`, created in the
  migration) for the search box; `(status)`, `(employee_type)`,
  `(department_id)` for dashboard filters

## Alembic notes

- `alembic/env.py` reads `DATABASE_URL` from `app.core.config.settings`, so
  container/local/CI all share one source of truth.
- The initial migration was autogenerated, then hand-extended with:
  `CREATE EXTENSION pg_trgm`, the GIN index, the partial unique index, and
  the two SQL views. If you re-autogenerate later you may see diff noise
  around the views — they are intentionally not registered as ORM tables.
- `alembic downgrade base` cleanly drops views/extension/tables.
